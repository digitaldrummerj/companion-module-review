# API 2.0 Compliance Rules (baseline for every 2.x module)

Applies to `@companion-module/base` **2.0.x and above** (Companion 4.3+). These rules are the floor that 2.1+ modules must also meet. Never report items from `v2.1.md` from this file.

---

## 🔴 Critical — module won't build or load, or risks user data

### Project and tooling
| Check | Expected |
|---|---|
| `package.json` dependency | `@companion-module/base` must be **2.x**. An exact version (`2.0.4`) or `~2.N.x` is fine; a caret range (`^2.x`) is only 🟡 (see SKILL.md Step 1) |
| `@companion-module/tools` | **≥ 2.7.1**; v3.x is a drop-in replacement and is recommended |
| Module format | TypeScript modules (the template) are **ESM**: `"type": "module"` in `package.json`. Base v2 exports both `import` and `require` entries, so a plain-JS module may stay CommonJS (`module.exports = class …`). Don't flag that |
| tsconfig | Extends `@companion-module/tools/tsconfig/node22/recommended-esm` (or sets `"module"`/`"moduleResolution": "nodenext"`). The old `node22/recommended` with `Node16` settings is wrong for 2.x |
| Imports | Relative imports end in `.js`. With `verbatimModuleSyntax: true` (template default), type-only imports use `import type` / `type X` |
| CommonJS deps | Any `require()` of a CJS-only package must work under ESM (`createRequire(import.meta.url)` or a default import) |

### Manifest (`companion/manifest.json`)
| Check | Expected |
|---|---|
| `"type"` | `"connection"` (required since 2.0.4; missing it fails `companion-module-check`) |
| `"$schema"` | `"../node_modules/@companion-module/base/assets/manifest.schema.json"` (recommended) |
| `runtime.type` | `"node22"`. `node18` was dropped. `node26` is **only** valid at base ≥ 2.1, so it is 🔴 on a 2.0.x module |
| `runtime.api` / `apiVersion` | `"nodejs-ipc"` / `"0.0.0"` (the build fills it in) |
| Template placeholders | No value left from the template manifest: `your-module-name` / `companion-module-your-module-name` (id, name, repository, bugs), `module-shortname`, `A short one line description of your module`, `Your name`, `Your email`, `Your company`, `Your product`. `companion-module-check` rejects them |

### Entrypoint
| Check | Expected |
|---|---|
| Main class | `export default class ModuleInstance extends InstanceBase<ModuleSchema>` (CJS: `module.exports = class …`) |
| Upgrade scripts | Named export `export const UpgradeScripts = [...]` or `export { UpgradeScripts }` |
| `runEntrypoint(...)` | **Must not exist**. It was removed in 2.0 |
| `InstanceBase<T>` generic | `T` is an `InstanceTypes`-shaped object `{ config, secrets, actions, feedbacks, variables }`, **not** the config type |
| Lifecycle signatures | `init(config, isFirstInit, secrets)`, `configUpdated(config, secrets)`, `destroy()`, `getConfigFields()`. Declaring fewer trailing parameters (e.g. `init(config)`) is valid — flag only wrong types or order |

### Removed APIs (each is a compile error or a runtime failure)
| Removed / changed | Replacement |
|---|---|
| `parseVariablesInString(...)` on the instance **or** on the callback `context` | Remove. Companion parses `textinput` fields with `useVariables: true` and any field in expression mode before the callback runs |
| `checkFeedbacks()` with **no** arguments | `checkAllFeedbacks()`. `checkFeedbacks(id, ...ids)` needs at least one id |
| `setVariableDefinitions([{ variableId, name }])` array | Object form `setVariableDefinitions({ variableId: { name } })` |
| `setPresetDefinitions(presets)` single argument | `setPresetDefinitions(structure, presets)` (sections → groups → presets) |
| Preset `type: 'button'` + `category` | `type: 'simple'`, with membership declared in the structure |
| Preset `type: 'text'` | Removed. Use section/group `name`/`description` |
| `relativeDelay` on presets | Removed. All delays are relative |
| Feedback `subscribe` callback | Removed. `callback` runs on add and on every options change, and `unsubscribe` runs on delete/disable |
| `InputValue` type | `JsonValue` |
| `isVisible: (opts) => …` functions on option/config fields | Removed. The function is silently ignored, so the field is **always shown**. Migrate to `isVisibleExpression: '$(options:otherField) == 1'` — 🔴 blocking |

### Presets (v2) — common reviewer mistakes

v2 presets differ from v1 in three ways reviewers frequently get **backwards**. Do not apply v1 preset rules to a v2 module.

| | v1 (base `1.x`) | **v2 (base `2.x`)** |
|---|---|---|
| call | `setPresetDefinitions(presets)` | `setPresetDefinitions(structure, presets)` |
| `type` | `'button'` (and `'text'`) | **`'simple'`** (2.1+ also `'layered'` / `'alternatives'`) |
| grouping | `category: '<string>'` per preset | `structure` sections array — **no `category`** |

- `presets` is a flat object keyed by preset id; `structure` is an array of sections whose `definitions` are preset ids or groups.
- **Every preset id in `presets` must be referenced somewhere in `structure`**, or Companion warns *"preset definitions exist in presets but are not referenced by structure"* (🟡).
- A v2 preset using `type: 'simple'`, no `category`, and a two-argument `setPresetDefinitions(structure, presets)` is **correct**. Never tell the maintainer to switch to `'button'`, add a `category`, or collapse to one argument — those are v1.

### `useVariables` on non-`textinput` fields

Verified against the `@companion-module/base` 2.0.4 and 2.1.3 typings:
- `useVariables` is declared **only** on `textinput`, where it turns on variable parsing in *value*-mode text.
- Every other field type (`number`, `dropdown`, `checkbox`, …) gets variables through **expression mode** instead, unless it sets `disableAutoExpression: true`.

The declaration's own note reads: "Even if this is false, users can toggle this field to expression mode to use variables".

| Module | What `useVariables: true` on a non-`textinput` field does | Report as |
|---|---|---|
| **TypeScript** | Compile error `TS2353: Object literal may only specify known properties, and 'useVariables' does not exist in type 'CompanionInputFieldNumber<…>'` (or `…Dropdown` / `…Checkbox`), so the module **does not build** | 🔴 Critical, as a build failure. Fix: delete the property. |
| **JavaScript** | Nothing checks it, and Companion never reads it on that field type, so it is a no-op | 🟢 Low "redundant property". Fix: delete the property. |

In both cases:
- Do **not** tell the maintainer that variables don't work on that field. They do, through expression mode.
- The v1 finding *"`useVariables` on a `number` field is ignored / a dead property"* is not a functional defect in 2.x. Report it only as described in the table.

### Upgrade scripts — wrapped option values
In 2.0, upgrade scripts receive every action/feedback option, and feedback `isInverted`, **wrapped**:

```ts
{ isExpression: false, value: 1 }              // previously just: 1
{ isExpression: true, value: '$(local:x) + 1' } // user-entered expression
```

A script that reads or writes `action.options.foo` as a raw value is 🔴, because it corrupts user data. It must read `.value`, check `.isExpression`, and write the wrapped shape back. Existing scripts must never be removed or reordered (they are positional).

## 🔴 Uses features from a later API version (2.0.x modules only)

Apply this section only when base resolves to **2.0.x**. Each item is a 🔴 finding: it fails to typecheck against 2.0 typings, or Companion drops/ignores it. Fix: bump base to `~2.1.x` (and require Companion 5.0+, then review with `references/v2.1.md`) or remove the usage.

- `hasResult`, or a `result` key in an action schema
- `context.signal` in any callback
- Preset `type: 'layered'` or `type: 'alternatives'`, `elements`, or composite elements / `setCompositeElementDefinitions`
- `internal:*` action/feedback ids in presets (the host drops them with a warning on pre-2.1 modules)
- `localVariables` entries with `variableType: 'feedback'`
- `affectedProperties` (harmless at runtime, but not in the 2.0 types)
- `manifest.runtime.type: "node26"`
- `CreateUseActionResultStoreUpgradeScript` (needs ≥ 2.1.1)

## 🟠 High — breaking-API misuse

| Check | Expected in 2.0 |
|---|---|
| `isVisibleExpression` in **action/feedback** options | May only reference fields that have `disableAutoExpression: true`, because a field driven by an expression has no static value to test |
| `textinput` `required: true` | Replaced by `minLength: 1` |
| `optionsToIgnoreForSubscribe` | Replaced by the allowlist `optionsToMonitorForSubscribe`. Actions with `subscribe`/`unsubscribe` should set it; when unset, every option change re-subscribes |
| `learn` callbacks | Return **only** the learned option(s) (`Partial<options>`). Returning the full options object overwrites user expressions |
| Advanced feedback `imageBuffer` | Must be a **base64 string** (`buffer.toString('base64')`), not a `Buffer` |
| Config type | Must satisfy `JsonObject`. Use a `type ModuleConfig = { … }` **alias**; an `interface` has no index signature and fails `InstanceTypes`. Values must be JSON-safe |
| Callback option casts (`action.options.x as string`) | Options are typed from the schema. Casts usually mean the schema is missing or wrong (🟡 if the schema exists) |
| Expression validation | Computed values are validated against the field. `number` is coerced, then rejected outside `min`/`max` unless `clampValues: true` (`asInteger: true` rounds). `dropdown` must match a choice unless `allowCustom: true`. On failure the action or feedback is **skipped as if disabled**, so check that min/max and choices fit real user values |
| `allowInvalidValues: true` | Only where the callback really handles out-of-range or unknown values |
| `await tcp.send(…)` / `await udp.send(…)` (base helpers) | `send()` is synchronous in 2.x (`TCPHelper` → `boolean`, `UDPHelper` → `void`; errors go to `'error'`). Code that awaits it or relies on rejection should use `sendAsync()`. `tsc` doesn't flag it |
| Fields read after removing `parseVariablesInString` | Must have `useVariables: true`, otherwise users' `$(…)` silently stops resolving (v1 parsed any string passed in) |
| `CreateConvertToBooleanFeedbackUpgradeScript` in `UpgradeScripts` | In base 2.1.3 it copies the wrapped `{ isExpression, value }` option into `feedback.style`. Flag it, and suggest an in-place literal-moving script (**companion-v1-to-v2-expression-upgrades** → `references/scripts.md`) |

## 🟡 Medium — recommended for 2.0

- **Numbers in `textinput`:** in 2.x a `textinput` is no longer *required* for a numeric option to accept variables (any field can use expression mode). Converting such a field to `type: 'number'`, with an upgrade script that calls `FixupNumericOrVariablesValueToExpressions` (`FixupBooleanOrVariablesValueToExpressions` for booleans), is optional hygiene, not a prerequisite. Don't push it where an empty value means "not provided" — that changes behaviour.
- **Dropdown ids:** they should be friendly strings (`'mute'`, not `'ch1=0'`), because users type them in expression mode.
- **Fields that make no sense as expressions** (e.g. an on/off/toggle choice): set `disableAutoExpression: true`. Add `expressionDescription` where expression input needs guidance.
- **`sortName`:** use it on actions/feedbacks to control ordering without renaming.
- **Logging:** prefer `this.log(level, msg)` or `createModuleLogger('Prefix')` over `console.*`, which only reaches the debug log.
- **Bonjour:** `manifest.bonjourQueries` may set `addressFamily: 'ipv4' | 'ipv6' | 'ipv4+6'` when the device needs it.
- **Feedback `previousOptions`:** `callback` receives `feedback.previousOptions`. Use it to detect option changes instead of re-subscribing.
- **Presets:** use `localVariables` and `type: 'template'` groups instead of generating hundreds of near-identical presets.
- **Typed definitions:**
  - Actions/feedbacks should be built against the schema so ids and options are type-checked: `setActionDefinitions` and `setFeedbackDefinitions` typed from `ModuleSchema`, and presets typed with `CompanionPresetDefinitions<ModuleSchema>`.
  - Hand-rolled v1 types (`CompanionPresetExt`, `InstanceBaseExt` with `[x: string]: any`) are no longer needed.
